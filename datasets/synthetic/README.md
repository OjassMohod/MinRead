# minread synthetic evaluation dataset

All people and conversations in this dataset are fictional. These files are test
inputs and human-authored expected findings, not outputs generated by an AI model.
Never use expected labels as application analysis responses.

See [the measured API budget](TOKEN_BUDGET.md) for dataset size, estimated tokens,
free-tier testing/demo capacity, and rate-limit scheduling.

## Files and splits

- `conversations.json`: 12 inputs with ordered messages, stable IDs, selected user,
  timezone, reference time, and paste-ready text.
- `expected.json`: expected semantic findings, source IDs, ambiguity, and things
  the app must not infer. Keep this file out of model requests and browser bundles.
- `manifest.json`: eight development IDs and four held-out evaluation IDs.

Use only development cases when adjusting prompts. Freeze prompts before running
the held-out split. Because these examples are stored in the repository, held-out
means excluded from prompt tuning, not a secret benchmark. After repeated tuning
against those results, create fresh unseen cases for a credible final check.

## How to use

For a manual check, paste a case's `raw_text` into the app and enter `selected_user`.
For a programmatic check, pass the ordered messages and available time context.
Never pass the split, case title, expected findings, or forbidden inferences to the
model. Missing timestamps must stay missing; the reference time is not evidence
of when an undated message was written.

Labels specify meaning rather than exact summary wording. ISO deadline values
use the explicit `Asia/Kolkata` context. Labels with null dates prohibit inventing
a normalized date. Supporting IDs must be present, and their content must actually
support the claim. Equivalent wording and additional genuinely supported findings
are acceptable; do not reward unsupported additions.

Evaluate outstanding tasks separately from historical completed/cancelled items.
Historical items can appear in a recap, but must not become current obligations.
Decisions may also be mentioned in summaries without being tasks. Unclear items
should explicitly preserve their uncertainty.

`outstanding_user_task_indexes` and `high_priority_user_task_indexes` are zero-based
indexes into each label's `findings` array. High priority uses the fixed reference
time and the documented 24-hour rule. Inject that reference time in automated
evaluation; live manual runs at another time can legitimately produce different
urgency classifications.

`open_issue_indexes` and `confirmed_decision_indexes` identify expected findings
for the corresponding output sections. Open issues include unassigned work,
important unanswered questions, blockers, and unresolved decision conflicts.
Do not preserve an issue after a later message answers, assigns, or resolves it.

## Record results

For each real model run, record model/version, prompt version, split, elapsed time,
and the following outcomes without logging any real user's chat:

- Task precision: correctly extracted outstanding tasks / all extracted outstanding tasks.
- Task recall: correctly extracted outstanding tasks / all expected outstanding tasks.
- Owner and deadline correctness for matched findings.
- Evidence support: whether cited messages support each claim, not just valid IDs.
- Correction handling: later changes and completion/cancellation applied correctly.
- Forbidden inferences and unresolved ambiguity.
- Summary faithfulness: supported important developments without invented details.

When a denominator is zero, report N/A and the false-positive count rather than
calling it a perfect score. Check summaries semantically, not by exact text match.

Two development cases (dev-01 and dev-02) have now passed live Groq smoke checks,
including an assigned deadline, unanswered question, and corrected deadline.
The second check used the browser end-to-end. These checks used 4,222 tokens
in total; a complete dataset accuracy benchmark has not been run. Priority labels
remain dataset annotations; priority scoring is deferred in the MVP.

## Recorded evaluation and annotation review

An initial live run exercised all 12 cases; outputs, failures, and targeted
rechecks are recorded in [the evaluation report](../../docs/EVALUATION.md).
Source-check scoring accepts assignment citations without redundant acknowledgement
citations, but deadline corrections still require original and corrected evidence.
The dev-02 label now includes pending vendor quotes as an open dependency: a
promise to deliver does not establish receipt. Inputs were unchanged. Previous
recorded scores remain available alongside reviewed checks. Held-out cases have
now been exercised; use new unseen cases for future independent evaluation.
